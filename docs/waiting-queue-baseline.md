# 대기열 도입 전 기준선 측정

[대기열 설계](waiting-queue.md)의 전제가 사실인지 확인하고, 도입 후 비교할 기준선을 만든다.

측정일: 2026-08-13

---

## 1. 무엇을 확인하려 했는가

설계 문서의 전제는 두 가지였다.

1. **오픈 스파이크가 서비스 전체를 느리게 만든다** — 신청과 무관한 API까지 같이 느려진다
2. **유입량을 조절할 수단이 없다** — 오는 대로 전부 받는다

둘 다 근거 없는 추측이었다. 숫자로 확인한다.

## 2. 측정 환경

### 컨테이너 자원

| 서비스 | CPU | 메모리 | 비고 |
| --- | --- | --- | --- |
| backend | **1.0 코어** | 1GB | JVM heap 최대 70% (~700MB), G1GC |
| mysql | 1.0 코어 | 1GB | MySQL 8.0 |
| redis | 0.5 코어 | 512MB | `maxmemory 384mb`, `noeviction` |

### 애플리케이션 설정

| 항목 | 값 | 출처 |
| --- | --- | --- |
| 톰캣 최대 스레드 | **200** | Spring Boot 기본값 (별도 설정 없음) |
| HikariCP 최대 커넥션 | **10** | `DB_POOL_SIZE=10` |
| 홀드 시간 | 2분 | `application.hold-duration` |
| 만료 스위퍼 주기 | 10초 | `application.expire-scheduler-delay-ms` |

### 부하 생성기

k6 v2.1.0, **같은 머신**(호스트 8코어 중 backend에 1코어 할당, 나머지를 k6가 사용).

> **절대값을 일반화하면 안 된다.** CPU 1코어 제한과 부하 생성기가 같은 머신에 있다는 조건에
> 묶인 값이다. 같은 조건에서 잰 **상대 비교(부하 전 / 중 / 후)** 만 유효하다.

### 측정 대상 캠페인

```
정원(totalStock)  100
requiresPayment   false
```

결제를 끄면 외부 호출이 빠져 **재고 경합만 남는다.** 오버셀 여부를 깨끗하게 보기 위해서다.
결제 경로는 PG 호출이 끼어 스레드를 더 오래 점유하므로, 실제 부하는 이보다 크다.

## 3. 측정 방법

`load-test/baseline.js` — 두 시나리오를 **동시에** 돌린다.

| 시나리오 | 내용 |
| --- | --- |
| `apply` | 정원 100인 행사에 N명이 한꺼번에 신청 (15초 지점부터 30초간) |
| `browse` | 신청과 무관한 캠페인 조회를 초당 5회로 **처음부터 끝까지** |

`browse` 응답 시간을 **스파이크 전 / 중 / 후** 세 구간으로 나눠 담는다. 신청 API만 재면
"신청이 느리다"까지밖에 못 보고, 그것이 다른 API에 무슨 영향을 주는지는 보이지 않는다.

서버 자원은 `load-test/monitor.sh` 가 1초 간격으로 actuator에서 수집한다.

부하 스크립트는 로그인 API를 거치지 않고 `load-test/lib/auth.js` 가 서버와 같은 비밀키로
액세스 토큰을 직접 서명한다. 소셜 제공자 없이 원하는 수만큼 사용자를 만들기 위해서다.

## 4. 결과 — 지원자 수별 (정원 100 고정)

### 4.1 응답 시간

| 지원자 | 신청 성공 | 신청 p95 | 조회 p95 (전 → 중) | 조회 중간값(중) | 조회 최대(중) |
| --- | --- | --- | --- | --- | --- |
| 200 | 100 | 1.75초 | 49ms → **123ms** | 9.6ms | 1.17초 |
| 1,000 | 100 | 29.1초 | 30ms → **1.73초** | 14.3ms | 3.62초 |
| 5,000 | 100 | 28.1초 | 28ms → **2.59초** | 21.2ms | 3.58초 |
| 10,000 | 100 | 16.3초 | 22ms → **3.58초** | **1.52초** | 4.31초 |

스파이크가 끝나면 조회는 모든 경우 20~45ms로 회복했다. 영구 손상이 아니라 **부하 중에만
발생하는 저하**다.

### 4.2 서버·DB 상태 (1초 간격 샘플의 최대값)

| 지원자 | 톰캣 사용 스레드 | JVM 스레드 | DB 커넥션 사용 | DB 커넥션 대기 |
| --- | --- | --- | --- | --- |
| 200 | 86 / 200 | 123 | **10 / 10** | 34 |
| 1,000 | 165 / 200 | 221 | **10 / 10** | **75** |
| 5,000 | **200 / 200** | 221 | 1 | 미포착 |
| 10,000 | **200 / 200** | 222 | **10 / 10** | 6 |

두 가지를 읽을 수 있다.

- **톰캣 스레드는 지원자 수에 비례해 늘고 5,000명부터 포화**된다. 조회 API 저하와 곡선이 같다
- **DB 커넥션 풀(10)은 모든 구간에서 가득 찬다.** 다만 대기 큐 길이는 지원자 수에 비례하지
  않고 **1,000명에서 가장 길다(75)**

DB 대기가 1,000명에서 최대인 이유는 그 시나리오만 지원자 전원이 동시에 발사되도록 VU를
잡았기 때문이다(7장 참고). 그리고 지원자가 늘수록 매진 응답 비율이 올라가는데, 매진 경로는
Redis만 쓰고 DB를 건드리지 않는다. **DB 경합은 지원자 수가 아니라 "동시에 DB를 치는 신청
수"가 정한다.**

> 1초 간격 샘플링이라 순간 피크를 놓칠 수 있다. 5,000명 구간의 DB 대기는 포착하지 못했다.

## 5. 결과 — 처리 한계

`load-test/capacity.js` — 초당 500건에서 8,000건까지 계단식으로 올린다.

```
실제 처리량        약 300 req/s
보내지 못한 요청    312,021건   (VU 고갈로 k6가 발사 자체를 포기)
응답 시간          중간값 18.0초 / p95 22.7초
5xx               0건
톰캣 스레드        200 / 200 포화
```

**5xx가 0이라는 점이 중요하다.** 서버는 죽지 않는다. 대신 **전부 느려진다.** 에러가 나지
않으니 에러율 기반 모니터링에는 아무것도 잡히지 않는다.

포화 구간에서 **`/actuator` 응답이 17개 샘플 중 11개(65%) 실패**했다. 부하가 걸리면 관측
수단부터 먼저 눈이 먼다. 현재 `backend`에는 헬스체크가 없어 문제가 없지만, 붙일 때는
타임아웃과 실패 임계를 넉넉히 잡아야 포화 상태에서 컨테이너가 재시작되지 않는다.

> 이 300 req/s는 **가장 싼 요청** 기준이다. 정원 100인 행사라 첫 100건 외에는 전부 매진
> 응답이고, 매진 경로는 Redis만 쓰고 DB를 건드리지 않는다. DB를 타는 요청의 한계는 더 낮다.

## 6. 발견

### 6.1 정합성은 전 구간 무결하다 — 건드리면 안 되는 부분

**모든 시나리오에서 정확히 100건 성공.** 지원자가 100배(10,000명)로 늘어도 오버셀이 한 건도
없었고 잔여 재고는 항상 0이었다.

기존 Lua 원자 차감이 제 역할을 하고 있다. **대기열은 이 방어선을 그대로 두고 앞에 붙여야
한다.** 설계 문서 3.1의 "신청 API를 거의 그대로 둔다"는 결정의 근거다.

### 6.2 전제 1은 사실이다 — 주범은 톰캣 스레드 고갈

신청과 무관한 조회 API가 **최대 58배(30ms → 1.73초)** 느려졌고, 10,000명에서는 p95 3.58초까지
올라갔다.

원인은 두 겹이다.

| | 역할 |
| --- | --- |
| **톰캣 스레드 고갈 (200/200)** | **주 원인.** 조회 요청이 스레드를 잡지 못해 큐에서 대기 |
| DB 커넥션 경합 (10/10, 대기 최대 75) | 부 원인. 스파이크 초반 신청과 조회가 같은 풀을 두고 경쟁 |

10,000명 구간에서 DB 대기가 6에 불과한데도 조회 p95가 3.58초인 것이 근거다. **DB보다
스레드 풀이 먼저 무너진다.** 신청 요청이 스레드를 점유하는 동안 조회는 순서를 기다린다.

### 6.3 임계점은 "얼마나 느린가"가 아니라 "전면화되는가"에 있다

p95만 보면 200명부터 이미 나쁘지만, **중간값**을 보면 성격이 갈린다.

```
200 ~ 5,000명   중간값 10~21ms   일부 요청만 느림  (간헐적)
10,000명        중간값 1.52초    절반 이상이 느림  (전면적)
```

"가끔 느리다"와 "항상 느리다"는 사용자에게 완전히 다른 경험이다. **실질적 임계점은
10,000명 부근**이고, 그 전까지는 꼬리 지연으로 나타난다.

### 6.4 신청 API 지표만 보면 문제를 놓친다

신청 p95가 1,000명에서 29.1초인데 10,000명에서 16.3초로 **오히려 좋아졌다.**

매진 이후 요청은 Redis 2회로 끝나는 싼 경로라, 지원자가 늘수록 이 싼 요청의 비율이 올라가기
때문이다(1,000명 → 78%가 매진 응답, 10,000명 → 99%).

**부하가 늘었는데 신청 API 지표는 개선된 것처럼 보이고, 같은 시간에 조회 API는 계속
나빠지고 있었다.** 대기열이 필요한 이유는 "신청이 느려서"가 아니라 **"신청이 다른 것을
망가뜨려서"** 다.

## 7. 측정의 한계

- **1,000명 구간만 동시성 조건이 다르다.** VU를 지원자 수에 맞춰 1,000으로 잡아 전원이
  동시에 발사했고, 5,000·10,000은 1,500 VU로 나눠 보냈다. 1,000명의 신청 p95(29초)와 DB
  대기(75)가 유독 높은 이유다. 조회 지표 비교에는 영향이 없다
- **1초 간격 샘플링이라 순간 피크를 놓친다.** 5,000명 구간의 DB 커넥션 대기를 포착하지 못했다
- **부하 생성기가 같은 머신에 있다.** 절대값은 실제 운영 환경과 다르다
- **결제 없는 캠페인만 측정했다.** 결제 경로는 외부 호출이 끼어 스레드를 더 오래 점유한다

## 8. 대기열 도입 후 재측정 항목

같은 스크립트로 같은 조건에서 다시 잰다.

| 항목 | 기준선 | 목표 |
| --- | --- | --- |
| 조회 p95 (10,000명 스파이크 중) | **3.58초** | 스파이크 전 수준(~20ms) 유지 |
| 조회 중간값 (10,000명) | **1.52초** | 전면적 저하 없음 |
| 톰캣 사용 스레드 최대 | **200 / 200** | 포화 없음 |
| DB 커넥션 대기 최대 | **75** | 감소 |
| 신청 성공 건수 | **100** | **100 유지** (오버셀 0) |
| 조회 p95 (200명, 한산) | **123ms** | **나빠지지 않을 것** |

마지막 항목이 핵심이다. 한산할 때 느려지면 대기열은 순손실이다.

## 9. 재현 방법

```bash
docker compose up -d

# 지원자 수별
./load-test/monitor.sh mon.tsv &
k6 run -e APPLICANTS=10000 -e SPIKE_VUS=1500 load-test/baseline.js
kill %1

# 처리 한계
k6 run load-test/capacity.js
```

`monitor.sh` 결과는 탭 구분이며, 빈 값(actuator 무응답)이 섞이므로 집계할 때 `awk -F'\t'` 로
구분자를 명시해야 한다.

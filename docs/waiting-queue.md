# 대기열 설계

오픈 순간에 몰리는 트래픽을 대기열로 흡수한다. 이 문서는 **왜 필요한지**, **지금은 어떻게
동작하는지**, **무엇을 바꿀 것인지**, **무엇이 나아지는지**를 순서대로 적는다.

> 이 문서의 전제는 실제로 측정해 확인했다. 숫자는 [기준선 측정](waiting-queue-baseline.md)에 있다.

---

## 1. 왜 하는가

### 지금 구조가 가진 성질

신청 요청은 **오는 대로 전부 받는다.** 정원이 100인 행사에 1만 명이 몰리면 1만 개 요청이
그대로 애플리케이션 서버로 들어온다. 재고가 0이 된 뒤에 들어온 요청도 마찬가지다 —
매진이라는 답을 주기 위해 톰캣 스레드를 하나 잡고 Redis를 두 번 왕복한다.

정원은 100인데 **9,900번의 "실패를 처리하는 일"** 이 발생한다. 이 일은 아무 가치를 만들지
않으면서 서버 자원을 정확히 똑같이 소비한다.

### 그래서 생기는 문제

**1. 티켓 신청이 서비스 전체를 느리게 만든다.**

톰캣 스레드 풀과 DB 커넥션 풀은 애플리케이션 전체가 공유한다. 오픈 순간에 신청 요청이
스레드를 전부 점유하면, 그 시간 동안 캠페인 조회·목록·로그인 같은 **무관한 API도 같이
느려진다.** 행사 하나의 오픈이 서비스 전체의 장애처럼 보이게 된다.

**2. 사용자가 상황을 알 수 없어서 부하가 증폭된다.**

지금 매진 응답은 `409 SOLD_OUT` 한 줄이다. 내가 몇 번째였는지, 다시 시도하면 가능성이
있는지 알 수 없다. 사용자가 할 수 있는 합리적인 행동은 **새로고침을 반복하는 것**뿐이고,
그 행동이 다시 부하를 키운다. 부하가 커지면 응답이 느려지고, 느려지면 더 누른다.

**3. 유입량을 조절할 수단이 아예 없다.**

현재 코드에는 "얼마나 받을지"를 정하는 지점이 없다. 서버를 늘리는 것 외에는 대응할 방법이
없고, 스파이크는 몇 분이라 증설로 대응하기에도 맞지 않는다.

### 목표

> **평소에는 없는 것처럼 동작하고, 몰릴 때만 유입을 조절한다.**

한산할 때 대기열이 응답 시간을 늘리면 그건 순수한 손해다. 이 점을 설계와 검증의 기준으로
삼는다.

## 2. 지금은 어떻게 동작하는가 (As-Is)

### Redis 키

| 키 | 자료형 | 내용 |
| --- | --- | --- |
| `campaign:stock:{id}` | String | 남은 자리 수 |
| `campaign:state:{id}` | Hash | `requiresPayment`, `totalStock`. **키의 존재 자체가 "오픈됨"을 뜻한다** |

### 신청 흐름

`POST /campaigns/{id}/applications` → `ApplicationService.apply()`

```
1. campaign:state:{id} 조회          (Redis)  없으면 → 409 CAMPAIGN_NOT_OPEN
2. campaign:stock:{id} 차감          (Redis)  Lua 스크립트로 원자적 처리
      -1 반환 → 409 STOCK_NOT_INITIALIZED
      -2 반환 → 409 SOLD_OUT
3. DB에 신청 기록                     (DB)    무료면 즉시 확정, 유료면 PENDING
      실패하면 → 재고 복원 후 예외
```

### 요청 유형별 비용

| 상황 | Redis | DB | 결과 |
| --- | --- | --- | --- |
| 정상 신청 | 2회 | SELECT + INSERT | 201 |
| 매진 이후 | 2회 | 없음 | 409 |
| 중복 신청 | 3회 (차감 후 복원) | SELECT | 409 |

매진 이후 요청이 DB까지 가지 않는 것은 이미 잘 되어 있다. **병목은 DB가 아니라 동시에
처리 중인 요청 수 자체다.** 요청 하나가 톰캣 스레드를 잡고 있는 동안 다른 요청은 큐에서
대기한다. DB 커넥션 풀(10)도 스파이크 초반에는 가득 차지만, 매진 이후에는 신청이 DB를
타지 않으므로 스레드 풀이 먼저 무너진다.

정원 100에 10,000명이 몰렸을 때 실측값이다.

```
tomcat.threads.busy             200 / 200   스레드 풀 고갈
hikaricp.connections.pending            6   DB 대기는 오히려 짧다
무관한 조회 API p95              22ms → 3.58초
```

처리 한계는 **약 300 req/s** 이고, 그 이상에서는 5xx 없이 전부 느려진다.
자세한 내용은 [기준선 측정](waiting-queue-baseline.md) 참고.

### 이미 갖춰져 있어 재사용할 것

- **Lua 원자 처리** — `stockDecreaseScript`에서 쓰는 방식을 대기열에도 그대로 적용한다
- **상태 키를 스위치로 쓰는 패턴** — `campaign:state:{id}` 존재 여부로 오픈을 판단하는 것과
  같은 방식으로 대기열 가동 여부를 다룬다
- **DB가 최종 판정자** — 재고는 Redis가 관리하지만 신청 성립 여부는 DB 기록이 결정한다.
  이 원칙은 대기열이 생겨도 바뀌지 않는다

## 3. 설계 (To-Be)

### 3.1 큰 그림

```
[기존]  사용자 ──────────────────────────→ 신청 API ──→ 재고 차감 ──→ DB

[변경]  사용자 ──→ 입장 API ──┬─ 여유 있음 → 입장 토큰 즉시 발급 ─┐
                              │                                    ├─→ 신청 API ──→ 재고 차감 ──→ DB
                              └─ 막힘     → 순번 발급 → 폴링 ─────┘
                                                ↑
                                    통과 스케줄러가 초당 N명씩 꺼냄
```

**신청 API 자체는 거의 그대로 둔다.** 앞에 문지기를 하나 세우는 구조다. 기존 재고 차감
로직을 건드리지 않으므로 오버셀 방어는 지금 검증된 그대로 유지된다.

### 3.2 Redis 키

| 키 | 자료형 | 내용 | 수명 |
| --- | --- | --- | --- |
| `waitroom:enabled:{cid}` | String | 대기열 가동 중 표시 | TTL로 자동 종료 |
| `waitroom:queue:{cid}` | **ZSET** | 대기자. score=진입시각(ms), member=userId | 행사 종료 시 삭제 |
| `waitroom:admitted:{cid}` | String | 지금까지 통과시킨 누적 인원 | 행사 종료 시 삭제 |
| `waitroom:pass:{cid}:{uid}` | String | 입장 토큰 | TTL (기본 5분) |

**ZSET을 쓰는 이유**는 두 가지다. score를 진입 시각으로 두면 **먼저 온 사람이 앞에 서고**
(공평성), `ZRANK`로 순번을 O(log N)에 알 수 있다(진행률 표시). 단순 List로는 순번 조회가
O(N)이라 폴링에 쓸 수 없다.

### 3.3 입장 요청 — `POST /campaigns/{id}/entry`

Lua 스크립트 하나로 **판정과 발급을 원자적으로** 처리한다. 나눠서 하면 동시에 들어온
요청이 모두 "여유 있음"으로 판정되어 통과 상한을 넘긴다.

```
1. 이미 토큰이 있으면          → 그대로 반환      (새로고침 대응)
2. 대기열이 꺼져 있으면        → 즉시 토큰 발급   (한산한 시간대)
3. 대기자 0명 + 통과 여유 있음 → 즉시 토큰 발급   ★ 티켓 100 / 사용자 50이 여기
4. 그 외                       → 줄 세우고 순번 반환
```

응답이 두 가지로 갈린다.

```json
// 3번까지 걸린 경우 — 대기 화면 없이 바로 신청으로
{ "status": "ADMITTED", "token": "...", "expiresIn": 300 }

// 4번인 경우 — 이때만 순번 화면과 폴링
{ "status": "WAITING", "position": 3847, "estimatedSeconds": 76, "retryAfter": 5 }
```

**한산하면 왕복이 한 번 느는 게 전부이고, 그마저 Redis 조회 한 번이다.**

`retryAfter` 는 다음 폴링까지 기다릴 초를 **서버가 지정**한다. 대기 인원이 많을수록 늘린다.
클라이언트가 알아서 정하게 두면 새로고침 난사와 다를 바가 없다. 유입량을 실제로 조절하는
수단이 이것이다.

### 대기열이 실제로 줄이는 것

입장 요청 자체는 어차피 전부 받아야 한다. 1만 명이 오면 입장 요청 1만 개가 들어온다.
**대기열은 요청 수를 줄이지 않는다.** 줄이는 것은 동시 점유다.

```
동시 점유 스레드 = 초당 요청 수 × 요청당 처리 시간
```

신청 요청은 DB 까지 갔다 오느라 스레드를 오래 잡는다. 대기 중 폴링은 Redis 한 번이라
금방 끝난다. **같은 인원이 와도 오래 붙어 있는 요청이 짧은 요청으로 바뀌면 동시 점유가
줄어든다.** 여기에 `retryAfter` 로 폴링 간격까지 늘리면 요청 수도 함께 준다.

측정에서 같은 300 req/s 인데 톰캣 스레드가 싼 경로 17개, 비싼 경로 200개(포화)로 갈린 것이
근거다([기준선 5.5](waiting-queue-baseline.md)).

### 3.4 통과 처리 — 스케줄러

주기적으로 대기열 앞에서 N명을 꺼내 토큰을 발급한다. `ZPOPMIN`이 원자적이라 여러 서버가
같은 사람을 두 번 꺼내지 않는다.

```
이번에 통과시킬 수 = min(초당 통과 인원, 통과 상한 - 누적 통과 인원)
```

두 가지 한도를 함께 본다.

| 한도 | 값 | 역할 |
| --- | --- | --- |
| 초당 통과 인원 | **150** | 서버 보호 |
| 누적 통과 상한 | **남은 재고 × 배수(기본 2)** | 무의미한 대기 차단 |

150은 측정으로 정했다. 통과한 사람은 전부 DB까지 가는 비싼 요청이 되는데, 그 경로는
초당 200건에서 조회 p95 61.7ms로 버티다가 300건에서 972ms로 무너진다. 안전 상한 200의
75%를 잡았다. 근거는 [기준선 측정 5.5](waiting-queue-baseline.md) 참고.

배수를 두는 이유는 통과한 사람이 전부 신청을 끝내지는 않기 때문이다(이탈·결제 실패).
상한에 도달하면 뒷사람에게 **"매진 예상"을 미리 알려** 헛되이 기다리지 않게 한다.
배수의 적정값은 부하 테스트의 이탈률로 정한다.

### 3.5 대기열을 언제 켜고 끄는가

**시간 기준을 기본으로 한다.** `campaign.openAt`이 이미 있으므로 추가 데이터가 필요 없다.

```
오픈 시각 - 5분  →  waitroom:enabled 키 생성 (TTL 15분)
TTL 만료         →  자동으로 대기열 종료
```

혼잡도를 보고 자동으로 켜고 끄는 방식은 **채택하지 않는다.** 임계값 근처에서 켜졌다 꺼졌다를
반복(flapping)하기 쉽고, 그걸 막으려면 히스테리시스나 최소 유지 시간 같은 장치가 또 필요하다.
혼잡도는 **켜고 끄는 판단이 아니라 통과 속도를 조절하는 데만** 쓴다.

캠페인별로 아예 끌 수 있게 옵션(`useWaitingQueue`)을 둔다. 정원 5명짜리 행사에는 과하다.

### 3.6 신청 API 보호

```
POST /campaigns/{id}/applications
  헤더에 입장 토큰 필요

  대기열 꺼져 있음 → 토큰 검증 생략 (기존과 동일하게 동작)
  대기열 켜져 있음 → 토큰 없으면 403
```

신청이 성공하면 토큰을 삭제해 재사용을 막는다.

### 3.7 대기열이 유실되면 — 재고와 다르게 다룬다

재고는 DB에서 다시 계산할 수 있지만 **대기 순번은 Redis에만 있다.** DB에 없는 데이터라
날아가면 복구할 수 없다.

그래서 **대기열은 "잃어도 되는 것"으로 설계한다.**

| | 유실 시 |
| --- | --- |
| 재고 | DB 기준으로 재계산해 복구 |
| 대기 순번 | 복구하지 않는다. 전원 재진입 안내 |

이 선택이 성립하는 이유는 **대기열이 정합성의 근거가 아니기 때문이다.** 입장 토큰은
"신청 창구에 가도 좋다"는 허가일 뿐이고, 실제 재고 차감은 여전히 신청 API의 Lua
스크립트가 한다. **토큰이 남발되어도 정원을 넘겨 팔리지 않는다.**

> **대기열은 부하 조절 장치이지 재고 관리 장치가 아니다.**

이 원칙을 지키면 대기열의 내구성을 고민할 필요가 없어진다. 유실 시 손해는 "공평성이
깨지고 사용자가 다시 줄을 서야 한다"는 것뿐이고, 이는 돈 문제가 아니다.

## 4. 기존 대비 무엇이 해결되는가

| | 기존 | 변경 후 |
| --- | --- | --- |
| **유입량 조절** | 불가능. 오는 대로 전부 받음 | 초당 통과 인원으로 조절 |
| **다른 API 영향** | 스레드 점유로 전체가 느려짐 | 대기 중인 사용자는 폴링만 하므로 신청 경로를 점유하지 않음 |
| **매진 시 사용자 경험** | `409 SOLD_OUT` 한 줄. 새로고침 유발 | 순번·예상 시간 제공. 가망 없으면 미리 안내 |
| **헛된 처리** | 정원 100에 1만 건을 전부 처리 | 상한(정원×2)까지만 통과. 나머지는 게이트에서 종료 |
| **한산할 때** | — | **동일하게 유지** (즉시 통과) |
| **오버셀 방어** | Lua 원자 차감 | **변경 없음.** 기존 방어선 그대로 |

**오버셀 방어를 건드리지 않는 것이 설계의 전제다.** 대기열은 앞에 붙는 층이고, 검증된
재고 로직은 그대로 둔다.

## 5. 검증 계획

기존 k6 스크립트를 확장해 측정한다. **숫자 없이는 개선을 주장하지 않는다.**

### 측정 항목

| 항목 | 왜 재는가 |
| --- | --- |
| 신청 API p95 / p99 | 직접적인 개선 여부 |
| **무관한 API의 응답 시간** | 오픈 스파이크가 서비스 전체에 미치는 영향 |
| 5xx 발생 수 | 포화 시 서버가 무너지는지 |
| 톰캣 활성 스레드 / DB 커넥션 점유 | 자원 점유가 실제로 줄었는지 |
| 통과 인원 대비 실제 신청 수 | 상한 배수를 정하는 근거 (이탈률) |

### 시나리오

1. **스파이크** — 정원 100, 1만 요청 동시 유입. 대기열 전후 비교
2. **한산** — 정원 100, 50명. **응답 시간이 나빠지지 않았는지 확인** (도입의 전제 조건)
3. **오버셀** — 두 경우 모두 `성공 건수 ≤ 정원` 유지
4. **유실** — 대기열 가동 중 `FLUSHALL`. 오버셀이 발생하지 않는지 확인 (3.7의 주장 검증)

## 6. 하지 않는 것

범위를 명확히 해 둔다.

- **대기 순번의 영속화** — 3.7의 이유로 하지 않는다
- **매크로·부정 사용자 대응** — 별도 주제다
- **취소 대기(자리가 나면 알림)** — 대기열과 다른 기능이다
- **여러 서버에서 통과 스케줄러 중복 실행** — 현재 단일 인스턴스라 미룬다. 인스턴스를 늘릴
  때 분산 락이 필요하며, `ZPOPMIN`이 원자적이라 중복 통과는 없지만 통과 속도가 인스턴스
  수만큼 빨라진다

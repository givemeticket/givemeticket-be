# 캠페인 상세 조회 캐싱 실험

행사 상세 조회(`GET /campaigns/{shortCode}`)에 캐시를 넣고, 없을 때·Redis만 쓸 때·로컬 캐시까지
쓸 때를 같은 부하에서 비교한 기록이다.

## 결론 먼저

**캐시의 이득은 데이터 크기와 부하 수준에 달려 있다. 둘 다 작으면 아무 차이도 측정되지 않는다.**

| 조건 | 결과 |
| --- | --- |
| 안내문 9KB, 15 rps | 세 구성의 차이가 측정 잡음에 묻힌다 |
| 안내문 150KB, 15 rps | 요청당 할당이 793 → 698 → 561KB 로 갈린다 |
| 안내문 150KB, 한계까지 | 처리량 한계가 927 → 1,176 → **1,600 rps** 로 갈린다 |

로컬 캐시는 **처리량 한계를 1.7배** 끌어올렸다. 다만 그 차이는 800 rps 까지는 전혀 보이지 않다가
한계 근처에서만 드러났다.

참고한 글(<https://eunajung01.tistory.com/174>)의 "Redis 캐싱을 하면 GC 가 자주 발생한다"는
**이 프로젝트에서는 재현되지 않았다.** Redis 는 압축 덕에 어떤 크기에서도 DB 보다 적게 할당했다.
재현된 것은 그 글의 최종 결론 쪽이다 — 로컬 캐시가 Redis 캐시보다 GC 를 덜 낸다.

## 무엇을 캐싱했나

`CampaignService.getCampaignDetail` 안에서 `campaignRepository.findByShortCode` 한 방을 캐시가 받는다.

- 담는 값: [CampaignSnapshot](../src/main/java/kr/givemeticket/api/campaign/domain/CampaignSnapshot.java)
  — id, 제목, 정원, 오픈 시각, 상태, 안내문
- **담지 않는 값: 재고.** Redis 카운터가 진실이고 요청마다 달라진다. 담는 순간 캐시가 매진을 숨긴다
- 저장 형식: JSON 을 gzip 으로 압축 ([GzipRedisSerializer](../src/main/java/kr/givemeticket/api/global/config/GzipRedisSerializer.java))
- 끝난 행사는 캐시에 올리지 않는다 (상태가 CLOSED/DELETED 이거나 `detail.eventEndAt` 이 지난 경우)
- 무효화 지점 세 곳: 수정, 삭제, **오픈 스케줄러**

`campaign.cache.mode` 하나로 세 구성을 갈아 끼운다.

| mode | 구성 |
| --- | --- |
| `none` | 캐시 없음. 조회마다 DB |
| `redis` | Redis 캐시. 조회마다 네트워크 왕복 + 압축 해제 |
| `local` | 로컬 캐시(Caffeine) + Redis + pub/sub 무효화 |

## 실험 환경

호스트는 8코어 맥이고, 컨테이너 자원은 이렇게 묶었다.

| 컨테이너 | CPU | 메모리 |
| --- | --- | --- |
| backend | 2.0 (초기 실험은 1.0) | 1g, 힙 718MB (`MaxRAMPercentage=70`), G1GC |
| mysql | 1.0 | 1g |
| redis | 0.5 | 512m |

CPU 수를 적어 두는 이유는 **GC 워커 스레드 수를 결정하기 때문**이다. 1코어에서는 G1 이 워커
하나로 돌아 정지 시간이 비관적으로 나온다. 중간에 2코어로 바꾼 것도 그래서다.

측정은 프로메테우스 지표를 구간 적분해서 뽑는다. 계단마다 앞 12초·뒤 5초를 잘라낸다.

## 부하 시나리오

### soak.js — 조회·신청·확정 혼합

VU 하나가 `조회 → 신청 → 확정`을 돌고 1초 쉰다. 요청 3건이 한 사이클이다.

**캐시를 재는 데는 두 가지가 방해된다.**

1. 조회가 전체의 1/3 뿐이라, 나머지 2/3(DB 쓰기 + 결제 mock 호출)의 할당이 캐시 효과를 희석한다
2. 로그인 상태로 조회하면 `findByCampaignIdAndUserId`(내 신청 내역)가 매번 DB 로 나간다.
   사용자별이라 캐시할 수 없어서, 캐시를 켜도 조회당 쿼리가 2개에서 1개로 줄 뿐이다

### read-only.js — 조회 전용

위 두 문제를 없앤 시나리오다. **비로그인으로 조회만** 한다. 서버는 `userId == null` 이면
캠페인 조회 한 방으로 응답을 만들기 때문에, **캐시가 켜지면 DB 쿼리가 0건**이 된다.

캠페인 50개를 만들어 무작위로 돌린다. 하나만 두면 캐시 키가 하나뿐이라 히트율이 자동으로
100%에 수렴하는, 캐시에 지나치게 유리한 조건이 된다.

고부하에서는 k6 가 응답 본문을 버린다(`discardResponseBodies`). 116KB 응답을 초당 1,600개
받으면 k6 가 먼저 무너져서 서버 한계가 아니라 부하 도구 한계를 재게 된다.

## 실험 1 — 안내문 9KB, 15 rps (soak)

`RATE=5 DURATION=3m DETAIL_SIZE=3000`, 백엔드 1코어. Hikari 대기 0으로 포화가 아니다.

| 설정 | 할당/요청 | GC | p99 | 조회 p95 | 조회 p99 |
| --- | --- | --- | --- | --- | --- |
| none | 382.0KB | 9회 | 58ms | 21ms | 35ms |
| redis | 349.6KB | 8회 | 42ms | 17ms | 30ms |

| 설정 | 할당/요청 | GC | 조회 p95 | 조회 p99 | 승격 |
| --- | --- | --- | --- | --- | --- |
| redis | 349.9KB | 8회 | 21ms | 41ms | 0.0MB |
| local | 375.1KB | 9회 | 17ms | 25ms | 5.2MB |

**로컬 캐시가 GC 를 줄이지 못했다.** 오히려 할당이 7% 늘었다. 이유를 파고들어 보니:

```
로컬 히트    800회      ← 캐시는 제대로 작동했다
로컬 미스      5회      ← TTL 30초 × 161초 = 5.4회, 정확히 일치
Redis 호출     5회      ← 압축 해제가 805번에서 5번으로
```

역직렬화 800번을 없앴는데도 할당이 안 줄었다. **그 800번이 전체 할당의 2.4% 였기 때문이다.**

```
한 번당 약 25KB (압축 해제 7.5KB + readAllBytes 사본 7.5KB + Jackson String 약 6KB)
× 800회 = 약 20MB
구간 총 할당 836MB 중 2.4%
```

기대 절감(-2.4%)이 실행 간 잡음(±3.5%)보다 작다. **측정이 이 차이를 분해할 능력이 없다.**

지연은 달랐다. 조회 p99 가 41 → 25ms 로 39% 줄었다. 잡음보다 큰 차이라 읽을 수 있었다.
작은 데이터에서 로컬 캐시의 이득은 GC 가 아니라 **네트워크 왕복 제거**로 나타난다.

## 실험 2 — 안내문 150KB, 15 rps (soak)

같은 코드, 같은 부하에서 안내문만 3,000자 → 50,000자로 바꿨다.

| 설정 | 할당/요청 | GC | 총 정지 | 승격 |
| --- | --- | --- | --- | --- |
| none | 793.3KB | 20회 | 0.61s | 3.5MB |
| redis | 698.5KB | 17회 | 0.63s | 3.6MB |
| local | 560.9KB | 14회 | 0.57s | 0.0MB |

세 구성이 할당·GC 횟수 모두 단조롭게 갈린다. 차이가 12%, 20% 로 잡음(±3.5%)의 서너 배다.

Redis → 로컬로 바꾸면 조회당 **418KB** 가 사라진다(구간 조회 805건 기준). 페이로드 150KB 의
약 2.8배인데, 압축 해제 사본 + `readAllBytes` 사본 + Jackson 의 UTF-16 String 을 더한 값과 맞는다.

**예상이 하나 틀렸다.** Redis 가 DB 보다 나쁠 것으로 봤는데, 150KB 에서도 Redis 가 적게 할당했다.
DB 는 150KB 를 **압축 없이** 보내고 JDBC 가 String 을 만들고 Hibernate 가 엔티티를 만든다.
gzip 해제 비용을 물어도 그보다 싸다.

지연은 p99 45 / 53 / 52ms 로 평평했다. 150KB 응답을 직렬화해 내보내는 비용이 지연을 지배해서,
캐시가 앞단에서 아끼는 것이 묻힌다.

### 읽는 법

**800 rps 까지는 세 구성이 구분되지 않는다.** 전부 100% 를 채우고 p99 도 한 자릿수 ms 다.
차이는 한계 근처에서만 드러난다. 여유 있는 환경에서 캐시 효과를 재려 하면 아무것도 안 보인다.

**요청당 할당은 부하와 무관하게 일정하다** (765 / 570 / 168KB). 정상이라는 신호이자,
세 구성의 차이가 부하와 상관없이 유지된다는 뜻이다.

**한계는 할당 속도에서 온다.** `none` 과 `redis` 는 실제 달성한 할당 속도 704 / 660MB/s 에서
천장을 쳤다. 그 지점에서 총 정지 시간이 0.2s → 1.9~2.0s 로 10배 뛰고 p99 가 998 / 800ms 로
폭발했다. GC 오버헤드 자체는 1.3% / 0.9% 로 낮아 보이지만, 정지가 몰리면 꼬리 지연이 무너진다.

`local` 은 같은 1,600 rps 를 CPU 47%, 정지 0.52s, p99 68ms 로 처리했다. **아직 한계에 닿지도 않았다.**

## 정리

**크기에 따라 이득의 종류가 바뀐다.** 작은 데이터에서는 지연(네트워크 왕복 제거), 큰 데이터에서는
GC(역직렬화 제거)다. 하나만 보고 "캐시가 효과 없다"고 결론 내면 틀린다.

**Redis 캐시는 어떤 크기에서도 DB 보다 나았다.** 압축이 네트워크와 할당을 함께 줄이기 때문이다.
"Redis 캐싱이 GC 를 유발한다"는 서술은 압축하지 않거나 값이 MB 단위일 때 성립할 것으로 보인다.

**로컬 캐시의 값어치는 한계 처리량에 있다.** 평시 지연은 어느 구성이나 비슷하고, 부하가 몰릴 때
버티는 폭이 다르다. 티켓 오픈처럼 순간 부하가 튀는 서비스라면 이 차이가 곧 장애 여부를 가른다.

**남은 숙제: 요청당 168KB.** 로컬 캐시가 히트해도 사라지지 않는 바닥값이다. 응답 본문이
116KB 인데 그 1.5배를 할당한다. 응답 직렬화와 `ContentCachingResponseWrapper` 가 후보지만
아직 측정하지 않았다. JFR 로 할당 프로파일을 뜨면 나온다.

## 실패한 측정과 그 대책

측정을 믿을 수 없게 만든 것들이다. 같은 실수를 반복하지 않으려고 도구에 가드를 넣었다.

| 무슨 일 | 왜 위험한가 | 대책 |
| --- | --- | --- |
| VU 고정으로 포화 상태에서 비교 | 처리량 자체가 결과가 되어, 같은 부하 비교가 아니라 각자의 한계치 측정이 된다 | `RATE` 로 도착률 고정 |
| 다른 컨테이너가 CPU 2개를 먹음 | 같은 설정끼리(A/A) 차이가 A/B 차이보다 커짐 | 측정 전 CPU 경쟁 확인 |
| 측정 중 맥이 잠 | 측정 구간이 3분 대신 3시간 19분으로 기록됨 | 구간 길이 가드 + `caffeinate -i` |
| setup 이 실패했는데 표는 정상처럼 보임 | 전 요청이 404 인데 rps·GC·할당이 그럴듯하게 채워짐 | 체크 성공률 50% 미만이면 실행 폐기 |
| `ddl-auto=update` 가 손으로 한 ALTER 를 되돌림 | 컬럼이 TEXT 로 돌아가 큰 데이터 INSERT 가 500 | 매핑에 `columnDefinition` 으로 명시 |
| 실행마다 데이터가 쌓임 | 뒤에 도는 설정일수록 불리해짐 | `RESET_DB=true` |

## 재현

```bash
docker compose --profile obs up -d
```

계단식 부하 (핵심 실험):

```bash
caffeinate -i env BACKEND_CPUS=2.0 RATES=100,200,400,800,1600 STEP=60s DETAIL_SIZE=50000 CAMPAIGNS=50 MODES=none,redis,local ./load-test/ramp.sh
```

고정 부하 비교:

```bash
caffeinate -i env RATE=5 DURATION=3m DETAIL_SIZE=50000 RESET_DB=true ./load-test/gc-matrix.sh cache-off cache-redis cache-local
```

원자료는 `load-test/results/` 아래에 CSV·k6 출력·`gc.log` 로 남는다. 프로메테우스 보존은 7일이고
볼륨이 붙어 있어 컨테이너를 다시 만들어도 그래프가 남는다.

GC 지표를 화면으로 보려면 Grafana(`http://localhost:3001`)의 *GiveMeTicket — JVM/GC 메모리*
대시보드를 쓴다. 자세한 내용은 [gc-experiment.md](gc-experiment.md) 참고.

## 실험용 변경 (병합 전 원복 필요)

큰 데이터를 넣기 위해 도메인 제약을 임시로 풀어 두었다. 셋 다 코드에 `[실험용]` 주석이 붙어 있다.

| 파일 | 변경 | 원래 값 |
| --- | --- | --- |
| `CampaignDetail.java` | `MAX_CONTENT_LENGTH` | `5_000` |
| `CampaignDetail.java` | `@Column(columnDefinition = "LONGTEXT")` | 없음 (TEXT) |
| `CampaignDetailRequest.java` | `@Size` 메시지 | "content는 5000자를 넘을 수 없습니다." |

DB 컬럼 타입은 매핑을 되돌리고 백엔드를 재시작하면 Hibernate 가 알아서 맞춘다.
